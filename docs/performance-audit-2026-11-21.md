# Аудит производительности Albucore

21 ноября 2026 · [`main` на `d521624`](https://github.com/albumentations-team/albucore/tree/d521624bbeccf7afc7b6e8607bac33b7e5b78208) · 22 модуля и 9 413 строк Python в `albucore/`. В область проверки входят публичные операции, внутренние ядра, подготовка данных, выбор бэкенда и обмен буферами между NumPy и Torch CPU.

## В каком порядке работать

1. **Убрать целые буферы.** Начать с `convert_dtype(float16 → uint8)` через таблицу на 64 КиБ, линейного `resize3d` до одного среза и одношагового nearest для крупных C3 downscales. Для `box_blur` проверить удаление копии на FP32. Для batch `remap3d` при `N≥4, C>1` убрать удержание всех результатов перед `stack`. Это кандидат на экономию до почти одного выходного батча пиковой памяти.
2. **Делать статистику и применять таблицы за меньшее число проходов.** Повторно передать уже вычисленное среднее в `std`, проверить совместные min/max, убрать выделение и копирование отдельных каналов в `equalize_uint8`. Для `sqrt(uint8)` достаточно 256 заранее вычисленных float32 значений.
3. **Использовать структуру 3D-задачи.** Для nearest warp/remap с общей сеткой один массив индексов можно использовать для всех каналов и элементов батча. Для 3D-фильтров проверить OpenCV на XY и один специализированный Z-проход.
4. **Подбирать пороги после удаления лишней работы.** Переснять границы NumKong `cdist`, OpenCV на упакованных кропах, NumPy на произвольных strides и Torch на уже планарных данных. Отдельно проверять режимы с выделением результата, отдельным `out` и допустимым alias.

Числа ниже относятся к конкретным входам. Измеренный кандидат может потребовать отдельного региона dispatch. Остальные предложения — гипотезы с указанием того, какую работу они убирают и где могут проиграть. Действующие маршруты уже включают компактный CV16F C9 multiply на ARM, нативный half log на ARM и half exp на x86, новые LUT-маршруты для row crops и прямой `cv2.split` в существующие плоскости CHW для HWC. [Миграция на OpenCV 5.1](https://github.com/albumentations-team/albucore/pull/244), [обновление HWC → CHW](https://github.com/albumentations-team/albucore/pull/246).

## Какие бэкенды брать за baseline

| Бэкенд | Где маршрут уже оправдан | Где есть смысл сравнить заново |
|---|---|---|
| **NumPy** | FP32 scalar и full-field add/multiply, NumPy flip/transpose как views, wide редукции и произвольные strides, FP16↔FP32 storage casts на ARM, текущий FP32 GEMM. Для сложных выражений сравнивать ufunc с `out`, чтобы не штрафовать NumPy за необязательные temporaries. | Low-dimensional large `cdist`, где многократный обход result/scratch дорог. ## Что показал локальный скрининг

Apple M4 Max, macOS 27.0.1 arm64, CPython 3.11.11, NumPy 2.4.6, OpenCV headless 5.1.0.95, NumKong 7.8.7, StringZilla 5.3.2, Torch 2.15.0. Один поток. OpenCV `setNumThreads(0)` вернул один эффективный поток, Torch intra-op и inter-op оба по одному. NumKong работал с `neon=true` и `neonhalf=true`. Импорт Albucore подтверждён из отдельного снимка `d521624`, зависимости установлены в отдельную среду.

Базой служил публичный вызов Albucore. Прототипы включали подготовку аргументов, преобразования, ядро и выдачу результата. Для per-channel min/max отдельно измерялся компонент. Статические LUT построены один раз. Синтетические входы генерировались с seed 8043. FP32 — равномерные значения из [0, 1), FP16 — cast тех же данных, uint8 — полный диапазон. Сначала сверялись значения, форма и dtype, после прогрева чередовался порядок кандидата и базы. Первичная серия 2D использовала 31 пару. Серии повторения, 3D и cdist использовали по 21 паре. Отношение больше 1 означает, что кандидат быстрее. В таблице даны медианы и повтор там, где он был. Абсолютные времена заметно менялись между сериями, поэтому для определения порогов нужны стабильные повторы. Широкий прогон 2D остановлен на дорогой строке FP32 C9 per-channel keepdims. Глобальная `cv2.meanStdDev` требует проверки точности и стабильного fallback. Для FP32 массива 128×160×3 со значением `1e6`, где каждая третья строка содержала следующее представимое значение, NumPy вернул `std≈0,02952` при `eps=0`, а OpenCV вернул 0. Тот же эффект воспроизвёлся на смещениях от `1e4` до `1e8`. Сравнивать нужно весь быстрый путь вместе с защитой от потери дисперсии.

Медианное абсолютное отклонение времени базы и кандидата составило 74,42 и 15,12 мкс для повторного FP16→uint8, 5,22 и 0,51 мкс для linear до одного среза и 2,72 и 0,30 мс для повторного FP16 nearest C3 на глубине 64.

Базовый снимок `d521624` прошёл полный `pytest -q` в той же среде с явным путём к снимку для дочерних CLI-процессов. Результат — 8 318 passed и 3 skipped. Корректность прототипов проверялась отдельными сравнениями, описанными в таблице.

Для принятия отдельного ускорения выбрать формы из [матрицы benchmarks](https://github.com/albumentations-team/albucore/blob/d521624/benchmarks/README.md), добавить случаи вокруг ожидаемого crossover и сравнить старый и новый публичный вызовы на одном dtype. Для 2D дополнить C1/3/4/9, positive row crop, column/reversed stride, read-only, отдельный `out` и допустимый alias. Для 3D добавить изменённые по одной и всем осям размеры, глубину 1, разные N и C, half ties и nonzero fill. Сверять форму, dtype, численный допуск, выходную раскладку и содержимое входа. Для изменений аллокаций измерить свежий peak RSS на обеих платформах. [Политика приёмки Albucore](https://github.com/albumentations-team/albucore/blob/d521624/docs/maintaining/performance-policy.md).
